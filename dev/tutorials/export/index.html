Export a Model to a Bundle

ReactantServer serves bundles: directories that hold a compiled StableHLO program, its weights, and a manifest describing the tensors. This page builds a small Lux model and exports it into a bundle with ReactantServerExport. Export runs on the CPU and needs no server; the server never loads the export tooling or the model framework, only the bundle it writes.

Install

Add the export package and Lux to an environment:

using PkgPkg.add(["ReactantServerExport", "Lux"])

Build a model

Any Reactant-traceable model(x, ps, st) works; Lux is just the convenient way to build one. This MLP maps 4 features to 3. Lux puts the batch on the last axis, so a batch of inputs is a (4, batch) matrix.

using Lux, Random, ReactantServerExportmodel = Lux.Chain(Lux.Dense(4 => 8, tanh), Lux.Dense(8 => 3))ps, st = Lux.setup(Random.Xoshiro(0), model)example = randn(Float32, 4, 1)                     # (features, batch)

Export it

export_bundle(:lux, ...) traces the model once per requested batch size and writes the bundle into dir. The bundle's directory name is the model's name on the server.

export_bundle(    :lux, model, ps, st, example;    dir = joinpath("models", "mlp"), name = "mlp", batch_sizes = [1, 8])

The bundle is a directory with a manifest.yaml, one compiled program per batch size (model.b1.mlir and model.b8.mlir), and the shared weights.safetensors. The manifest names the input input and the output output (override with input_name and output_name), records their dtypes and shapes, and lists the compiled batch sizes.

A server answers requests of any size up to the largest compiled batch by padding a request to the next compiled size, and splits larger ones. Compiling more sizes trades startup compile time for less padding.

Check the bundle

A program must take exactly as many arguments as the manifest declares inputs plus the weights file holds tensors. export_bundle already refuses to write a bundle that disagrees, and bundle_arity_report reads the numbers back from any bundle, including one written elsewhere:

report = bundle_arity_report(joinpath("models", "mlp"))report.servable                                    # true

models/ is now a model repository: every subdirectory with a manifest.yaml is a servable model. Either serving path takes it as is: Serve a Model from a Julia session, or Serve on One GPU with the container image. Bundles documents the manifest, custom pre- and postprocessing through a bundle's model.jl, and the multi-input and PyTorch frontends.

bundle_arity_report(dir) -> NamedTuple

Read a written bundle's three numbers and say whether they agree: the inputs its manifest.yaml declares, the tensors its weights.safetensors holds, and the arity of each compiled module.

export_bundle(frontend::Symbol, args...; kwargs...) -> dir

Export a model to a bundle, naming the frontend explicitly so the call site is unambiguous:

export_bundle(:lux, model, ps, st, example_input; dir, name, input_name="input", output_name="output", batch_sizes=[1], provenance=Dict(), layout=:xla, compile_options=(;)) -> dir

Trace model(x, ps, st) (taking the first return as the output) at each batch size and write a bundle.
