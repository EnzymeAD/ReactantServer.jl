Security

ReactantServer is designed to run on a trusted network behind your own perimeter. Be aware of the following before exposing any endpoint:

  • Cleartext h2c. All gRPC traffic (worker and gateway) is cleartext h2c. TLS settings are parsed by the gateway config but not yet enforced; a configured cert triggers a startup warning.
  • No authentication or authorization on the KServe data plane, the worker control-plane RPCs (residency and policy), the gateway's own scheduling control plane (GatewayControlService, which can repack the fleet and change a model's replica count and routing at runtime), or the Prometheus metrics listener (which binds 0.0.0.0:8002 by default). The control plane is mutating, so treat access to the gRPC ports as administrative access.
  • Trusted bundles. A bundle's optional model.jl executes arbitrary Julia in the server process, so bundles are trusted input. Only serve bundles you built or audited; see Bundles.
  • Shared memory is a local trust boundary. Client-registered regions and the optional node-shared host-weight store live in /dev/shm; the shared weight regions default to mode 666 (world-writable) for friction-free sharing. Set runtime.shared_host_weights_mode: "660" on production or multi-user systems. A worker identifies a registered region by the object it mapped (device and inode), not by its name: registering a name that is held by another client's object that still exists fails with ALREADY_EXISTS instead of redirecting that client's traffic, and registrations whose object was unlinked or recreated are dropped. An object a crashed client left behind stays registered until it is removed from /dev/shm. Before every copy into or out of a registered region, and before touching a slot control word, a worker checks that the object still covers the range and that the range's pages exist (allocating them unless fstat shows every page of the object allocated), so a client that shrinks its object after registering it gets FAILED_PRECONDITION, and a range whose pages a full /dev/shm cannot hold gets RESOURCE_EXHAUSTED, rather than the worker touching a page that is not there, which would kill it with SIGBUS. The check and the copy are not atomic: a client that shrinks its object, or frees its pages while /dev/shm is full, during the worker's copy can still kill the worker with SIGBUS. Closing that window would take a SIGBUS handler around the copy, or file seals, which shm_open objects do not support. A local process that can register a region can therefore still crash a worker on purpose; only let trusted clients register regions.
  • Internal errors are redacted by default. With grpc.error_detail: redacted (the default, set node-wide under global.grpc), a client is told of a failure inside the server only by a request id and the worker's (or gateway's) name, and the gateway never names a worker by host and port; the exception and backtrace go to that server's log under the same id. Keep full, which sends the exception text to clients, to development and testing. See Node Configuration.
  • The receive size limit is a memory commitment. The worker and gateway gRPC servers allocate a buffer of a request message's full declared length as soon as its 5-byte length prefix arrives, before the payload. A client that sends a length prefix and nothing more therefore makes the process hold a buffer of up to grpc.max_recv_msg_bytes (512 MiB by default) for as long as the request stays open, and can do so on as many requests at once as the server admits. Where untrusted or unauthenticated clients can reach a worker or the gateway, lower grpc.max_recv_msg_bytes on both to the largest inline message the deployment needs (see Node Configuration; tensors sent through shared memory do not count). On a node set it in global.grpc, which the supervisor mirrors into the embedded gateway. An environment override wins over the YAML value, so also set or clear INFERENCE_SERVER_GRPC_MAX_RECV_MSG_BYTES (workers) and REACTANT_GATEWAY_GRPC_MAX_RECV_MSG_BYTES (gateway).
  • HTTP/2 Rapid-Reset protection is off by default, on the workers and the gateway. That protection disconnects a client once it has reset more than 200 streams on a connection, which every client that gives up on calls eventually does, and gRPCClient-based clients can then hang until their deadline. A connection may therefore reset any number of streams, and what bounds a client that resets them is the inbound cap, past which calls are shed with RESOURCE_EXHAUSTED (endpoints.max_concurrent_requests on a worker, grpc.max_concurrent_requests_per_worker on the gateway). Where untrusted clients can connect, keep those caps above 0, or turn the protection on and accept the cut-off: on a node, global.grpc.rapid_reset_protection: true (or REACTANT_RAPID_RESET_PROTECTION=true on the node container) turns it on for every worker and the embedded gateway at once. See Rapid-Reset protection for which setting wins.
